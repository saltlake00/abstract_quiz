# 중간 보고서 02: 커스텀 이미지 추가 및 삼각형 개수 확장 기능에 대한 기술·수치 분석

## 1. 맥락 및 목적
1차 구현 및 GitHub Pages 배포 완료(`e2ea82b`) 이후, 사용자 정의 이미지를 문제로 추가하는 기능과 그림을 구성하는 삼각형 개수($N$)를 늘리거나 조절하는 기능의 도입 타당성을 검토했습니다. 코드를 즉시 수정하기 전에 현행 알고리즘(`scripts/01_build_quiz_dataset.py`)과 네트워크 동기화 구조(`js/net.js`, `js/app.js`)를 분석하여 과학적 근거에 기반한 설계 계획(`docs/추가기능_계획서_이미지추가_및_삼각형확장.md`)을 수립했습니다.

## 2. 핵심 분석 및 가설 검증

### 2.1 삼각형 개수($N$) 증가에 따른 RMSE 감소율과 스케일 하한 분석
* **분석 대상**: `intermediate_results/rmse_convergence.csv`의 15개 문항 실측 수렴 데이터 및 `scripts/01_build_quiz_dataset.py`의 4단계 반경 스케줄러.
* **관찰 결과**:
  * 15개 문항의 평균 RMSE는 $k = 0$일 때 $69.18$, $k = 25$일 때 $45.49$, $k = 50$일 때 $38.88$, $k = 100$일 때 $32.65$, $k = 200$일 때 $26.19$, $k = 260$일 때 $23.99$로 감소합니다.
  * 구간별 도형 1개당 평균 RMSE 감소량($-\Delta \text{RMSE} / \Delta k$)을 계산하면:
    * $k \in [0, 25]$: 도형 1개당 $-0.948$ 감소
    * $k \in [25, 100]$: 도형 1개당 $-0.171$ 감소
    * $k \in [100, 200]$: 도형 1개당 $-0.065$ 감소
    * $k \in [200, 260]$: 도형 1개당 $-0.037$ 감소
* **결론 및 방법 선택**:
  * 현행 마지막 단계($progress \ge 0.78$)의 삼각형 반경 범위가 $R \in [4, 13]\text{ px}$로 고정되어 있어, $N > 260$ 이후에는 미세 특징점(눈동자, 글자, 장신구)보다 넓게 퍼진 반투명 패치가 덧칠되는 한계가 있습니다.
  * 따라서 삼각형 개수를 $N = 400 \sim 600$개로 확장할 때는 단순 반복 횟수 증가가 아니라, $R \in [2, 6]\text{ px}$ 및 $\alpha = 0.60$의 **제5스케일(초미세 디테일 구간)**을 도입해야 도형 1개당 유효 정보량 이득을 유지할 수 있습니다.

### 2.2 클라이언트 실시간 삼각형 분해 알고리즘의 연산 복잡도 검증
* **가정**: 브라우저에서 사용자가 업로드한 사진을 서버 없이 즉시 삼각형으로 분해하려면 메인 스레드 블로킹을 피하고 1~2초 내에 연산이 끝나야 합니다.
* **방법 비교**:
  1. **전체 픽셀 누적 확률 샘플링 (현행 Python 방식)**: 매 스텝마다 $W \times H = 39,600$ 픽셀의 오차 제곱합 배열을 정규화하고 누적합을 구하므로 $N = 400$일 때 약 $1.58 \times 10^7$회의 배열 순회가 추가됩니다.
  2. **토너먼트 샘플링 (Tournament Selection, $K = 4 \sim 6$)**: 무작위 픽셀 $K$개를 상수 시간 $O(K)$에 뽑아 그중 현재 오차 $\|T(x,y) - C(x,y)\|_2^2$가 가장 큰 위치를 삼각형 중심점으로 선택합니다.
* **타당성 결론**: 토너먼트 샘플링은 고오차 영역에 대한 선택 편향(Selection Bias)을 그대로 유지하면서도 중심점 선택 비용을 $O(W \cdot H)$에서 $O(1)$로 줄여, 브라우저 `Float32Array` 기반 연산 시 $N = 400$개 분해를 약 $0.8 \sim 1.5$초 내에 수행할 수 있습니다.

### 2.3 멀티플레이 패킷 대역폭 및 스포일러 방지 설계
* **문제 정의**: 400개 삼각형 문항의 JSON 직렬화 크기는 약 $25\text{ KB}$입니다. 이를 400ms 주기의 `STATE_SYNC`에 포함하면 호스트가 게스트 7명에게 브로드캐스트할 때 높은 네트워크 부하가 발생합니다.
* **해결책**:
  * 라운드 시작(`countdown`) 시점에 정답(`answers`, `title`)을 제외한 폴리곤 배열(`polygons`, `bg`, `width`, `height`, `hint1`, `hint2`)만 `QUESTION_DATA_SYNC` 이벤트로 1회 전송하고 게스트 측 메모리 캐시에 보관합니다.
  * 라운드 종료(`round_result`) 시점에만 정답 문자열을 전송하여, 네트워크 대역폭 절감과 브라우저 개발자 도구 스포일러 방지를 동시에 달성합니다.
